# 第四章实验手册指南 ：构建智能知识系统的工程化基座

## 1. 实验概览

实验目标：本实验将引导你从零开始，应用软件工程的方法论来重构你的个人知识库。你将不再把笔记仅仅看作文本，而是将其视为“代码”。

核心任务：

1. **环境搭建**：建立基于 Git 的“知识仓库”，并实践功能分支工作流。
2. **数据重构**：设计面向 RAG 的 YAML 元数据架构，并进行原子化拆分。
3. **交互设计**：编写基于 COSTAR 框架的结构化提示词。
4. **代理模拟**：手动模拟“规划-执行-反思”的 Agentic Workflow 闭环。

所需工具：

- 本地编辑器（Obsidian）
- Git客户端
- LLM 访问权限（Qwen、DeepSeek、Kimi 或ChatGPT等）
- GitLink账号

---

## 2. 任务一：知识即代码——Git 工作流实战

**理论对应**：讲义 4.1.2（功能分支工作流） & 4.1.4（提交信息规范）

### 步骤 1.1：初始化知识仓库

1. 在本地创建一个新文件夹，命名为 `knowledge-engineering-lab`。

2. 初始化 Git 仓库。

3. 创建 `README.md`，写入一行标题“智能知识工程实验库”，并进行第一次提交（Commit）。

    - _命令行参考_：`git commit -m "chore: init project"`


### 步骤 1.2：实践“功能分支工作流” (Feature Branch Workflow)

**场景**：你需要撰写关于“RAG 技术原理”的新笔记。不要直接在 `main` 分支修改。

1. **创建分支**：基于 `main` 创建一个新分支，命名规范需具备语义性。

    - _建议命名_：`feat/rag-principles`

2. **创建内容**：在分支中新建文件 `RAG-Concepts.md`，随便写入一些关于 RAG 的定义（草稿即可）。

3. **原子提交**：进行一次提交，应用 Conventional Commits 规范。

    - _错误示范_：`git commit -m "add notes"`

    - _正确示范_：`git commit -m "feat: add initial definition of RAG concepts"`

### 步骤 1.3：模拟冲突与合并

1. 切换回 `main` 分支。

2. 在 `main` 分支中修改 `README.md`，增加一行：“维护者：[你的名字]”，并提交。

3. 将 `feat/rag-principles` 分支合并回 `main` 分支（Merge）。

4. **思考**：如果有冲突产生，该如何像讲义 4.1.1 中提到的那样进行“辩证解决”？

## 3. 任务二：数据层构建——面向 RAG 的元数据设计

**理论对应**：讲义 4.2.1（YAML Frontmatter） & 4.2.2（原子化与合成问题）

### 步骤 2.1：定义 YAML Schema

在 `RAG-Concepts.md` 文件顶部，插入 YAML Frontmatter。你需要严格按照讲义 4.2.1 的建议，包含以下字段：

YAML

```
---
uuid: [使用工具生成一个UUID，或手动填一个唯一码]
aliases: [检索增强生成, Retrieval-Augmented Generation]
tags: [AI/RAG, Knowledge/Engineering]
type: Concept
status: Seedling
visibility: Public
related_questions:
  - 什么是RAG技术？
  - RAG如何解决大模型的幻觉问题？
---
```

### 步骤 2.2：原子化拆分与合成问题

**场景**：你有一段关于 RAG 流程的长文本（如下）。请利用 LLM 辅助将其拆分为“原子化单元”，并生成“合成问题”。

**原始文本（请复制给 LLM）**：

> RAG 的流程主要分为检索和生成两个阶段。首先，系统将用户的查询转换为向量，在向量数据库中搜索相关的文档块。然后，将检索到的文档块作为上下文，连同用户的问题一起输入到大语言模型中。这样模型就能基于外部知识回答问题，减少了胡编乱造的情况。

**操作要求**：

1. 使用 LLM 将上述文本拆解为独立的原子陈述（Atomic Statements）。

2. 让 LLM 为每个陈述生成 2-3 个潜在的用户查询问题（Synthetic Questions）。

3. 将结果填入你的 `RAG-Concepts.md` 正文中。

## 4. 任务三：交互层设计——编写 S.C.O.R.E协议

**理论对应**：讲义 4.3.1（S.C.O.R.E 模型）与 讲义 2.4（S.C.O.R.E 详解）

### 步骤 3.1：设计结构化 Prompt

**场景**：你需要一个 AI 助手帮你审查刚才写的 RAG 笔记，并将其核心逻辑转化为一张 **Mermaid 流程图** 代码，以便插入到文档中。请根据 **S.C.O.R.E 模型** 填写以下提示词协议。

**请填空完成 Prompt**：

| 维度                      | 提示词设计 (请补全括号内内容)                                                                                                               |
| :---------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| **S (Setting)**<br>角色设定 | 你是一位 **[请填写：资深的知识可视化专家 / 技术文档工程师]**，精通 Mermaid 语法与技术概念图解。                                                                      |
| **C (Context)**         | [cite_start]以下是我关于 RAG (检索增强生成) 的 **[请填写：原子化笔记文本 / 草稿]**。你需要理解其中的处理流程。                                                         |
| **O (Objective)**       | [cite_start]你的任务是将上述文本转化为 **[请填写：标准的 Mermaid 流程图代码]**。请提取关键步骤（检索、增强、生成）并展示数据流向。                                                |
| **R (Requirements)**    | 1. 仅输出 Mermaid 代码块，不要包含解释性文字。<br>2. 使用 `graph TD` (从上到下) 布局。<br>3. **[请填写：节点形状要求，如：使用矩形表示处理步骤，菱形表示判断]**。<br>4. 确保代码语法正确，可直接渲染。 |
| **E (Evaluation)**      | 在输出代码前，请先 **[请填写：自检机制]**：<br>1. 是否包含了“检索”和“生成”两个关键环节？<br>2. 是否存在语法错误？<br>如果自检未通过，请修正后再输出。                                      |

### 步骤 3.2：测试与迭代

1. 将上述 Prompt 发送给 LLM。

2. 检查输出结果是否符合预期。如果不符合，调整 Prompt 中的 **Constraints (约束)** 部分。

## 5. 任务四：代理层模拟——人工运行 Agent 循环 (25分钟)

**理论对应**：讲义 4.4.2（规划-工具-反思模式） & 4.4.3（多代理编排）

**背景**：由于我们尚未部署 Python 环境，本任务将通过“手动运行 Agent”的方式，深刻理解 Agent 的思考逻辑。你将扮演“运行环境”，LLM 扮演“Agent”。

### 步骤 4.1：初始化 Agent (规划模式)

向 LLM 发送以下指令（这是 Agent 的 System Prompt）：

> 你现在是一个智能研究代理 (Researcher Agent)。你的目标是撰写一份关于“GraphRAG vs VectorRAG”的对比简报。
>
> 请不要直接生成报告。请先使用 [规划模式]，列出你需要执行的子任务步骤（Plan）。

### 步骤 4.2：模拟工具调用 (工具使用模式)

当 LLM 列出计划（例如：1. 搜索 GraphRAG 定义；2. 搜索 VectorRAG 定义...）后：

1. 你（作为运行环境）模拟工具执行。去搜索引擎或讲义中找到相关定义。

2. 将找到的信息“喂”回给 LLM。

    - _Prompt 示例_：`【系统消息】：工具 Search 运行结束。返回结果如下：[粘贴你找到的 GraphRAG 定义...]。请基于此结果执行下一步。`


### 步骤 4.3：触发自我修正 (反思模式)

当 LLM 生成最终简报草稿后，发送以下指令强制其反思：

> 停止。进入 [反思模式]。
>
> 请检查上述简报：
>
> 1. 是否引用了具体的参考文献？
>
> 2. 逻辑是否通顺？
>
>     如果有缺陷，请输出“Critique”（批评意见），并根据批评意见重新生成修正版（Refine）。
>
