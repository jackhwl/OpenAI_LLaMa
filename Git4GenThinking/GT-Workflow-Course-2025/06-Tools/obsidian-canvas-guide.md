
# Obsidian Canvas 可视化编排操作指南

这是一份基于 《第三章：结构化提示工程*》核心理念，专为本课程设计的 **Obsidian Canvas 可视化编排操作指南手册**。

这份手册不仅是软件操作说明，更是一份“认知编程”的规范文档。它定义了如何用图形语言表达复杂的 Prompt 逻辑，是完成 Lab 03 及后续 Agent 设计任务的必备工具书。

---

## **1. 理念：为什么需要“可视化编排”？**

在传统的提示工程中，我们习惯于在**线性**的聊天窗口（Chat Interface）中工作。这导致了三个问题：

1. **逻辑黑盒**：多轮对话后，很难看清推理的路径和依赖关系。
2. **语境遗忘**：早期的约束条件容易被模型（或用户自己）遗忘。
3. **难以调试**：当输出不理想时，很难定位是哪一步的 Prompt 出了问题。

可视化编排（Visual Orchestration）将 Prompt 从“文本流”升级为“拓扑图”。在 Canvas 中，每一个节点（Node）都是一个功能模块，每一条连线（Edge）都是数据流向。所见即所得（WYSIWYG）的不仅仅是笔记，更是你的思维逻辑。

## **2. 视觉协议 (Visual Protocol)**

为了确保工作流的可读性与可维护性，本课程制定了统一的**视觉编码规范**（Visual Coding Standard）。请在作业和项目中严格遵守。

### 2.1 节点色彩规范 (Color Coding)

我们使用色彩来区分节点的**功能属性**，模拟电路板的设计逻辑。

|**颜色**|**语义定义**|**功能描述**|**典型内容**|
|---|---|---|---|
|🟩 **绿色**|**Input / Context**<br><br>  <br><br>(输入层)|系统的原材料。模型推理所需的事实、背景、文档。|原始文章、数据表格、参考资料、用户需求|
|🟨 **黄色**|**Prompt / Logic**<br><br>  <br><br>(逻辑层)|系统的处理器。对模型下达的指令、约束和任务定义。|Role, Task, Constraints, Steps (结构化 Prompt)|
|🟥 **红色**|**Output / Artifact**<br><br>  <br><br>(输出层)|系统的产物。模型生成的结果。|初稿、摘要、代码、JSON 数据|
|🟦 **蓝色**|**Evaluation / Critic**<br><br>  <br><br>(评价层)|系统的裁判。对输出进行评分、反思或提出修改建议。|评分标准、Critic Prompt、反思日志|
|⬜ **灰色**|**Note / Comment**<br><br>  <br><br>(备注层)|解释说明。用于标注流程逻辑或分支条件。|“如果不合格则走这条路”、“需人工确认”|

### 2.2 连线与布局规范

- **流向**：严格遵循 **“从左到右”** 或 **“从上到下”** 的数据流向。

- **连线含义**：

    - `A -> B` 表示：A 的内容是 B 的**前置上下文 (Pre-context)**。
    - 在逻辑上，这意味着：`Prompt B 的输入 = Node A 的内容 + Node B 的指令`。

- **分支 (Branching)**：使用连线标签（Label）标记条件（如 "Yes", "No", "Score < 3"）。

## 3. 核心编排模式 (Orchestration Patterns)

掌握这三种基本图形结构，你就能构建 90% 的 AI Agent 逻辑。

### 模式 A：线性流水线 (The Pipeline)

最基础的结构，用于分步处理任务。

> **结构：** `[素材] -> [大纲 Prompt] -> [大纲结果] -> [正文 Prompt] -> [最终文章]`

- **适用场景**：长文写作、多步骤翻译、内容摘要。

- **操作要点**：确保每一步的输出（红卡）都连接到下一步的 Prompt（黄卡）作为输入。

### 模式 B：分支决策树 (The Decision Tree)

引入逻辑判断，处理复杂情况。

> 结构：
>
> [用户输入]
>
> |
>
> +---> (是技术问题?) ---> [技术专家 Prompt] ---> [代码解决方案]
>
> |
>
> +---> (是概念问题?) ---> [科普作家 Prompt] ---> [通俗解释]

- **适用场景**：客服自动分类、多风格内容生成。

- **操作要点**：利用连线上的 **Label** 功能（双击连线输入文字）标记判断条件。

### 模式 C：批评-修正闭环 (The Critic Loop)

实现自我进化的关键结构（EEIS 架构的核心）。

> 结构：
>
> [初稿(红)] -> [评价 Prompt(蓝)] -> [修改建议(蓝)]
>
> |
>
> v
>
> [初稿(红)] ----------------------> [修正 Prompt(黄)] -> [终稿(红)]

- **适用场景**：高精度文案、代码 Debug、逻辑推演。

- **操作要点**：修正 Prompt（黄卡）必须同时接收“初稿”和“修改建议”两个输入。

## 4. 实战操作流程

### 第一步: 初始化画布

1. `Cmd/Ctrl + P` 呼出命令面板，输入 `Create new canvas`。

2. 重命名文件为 `Project_Name.canvas`。

### 第二步：放置输入

1. **双击**画布左侧空白处，创建一个卡片。

2. 粘贴你的原始素材（如一段乱糟糟的会议记录）。

3. 点击卡片颜色盘，设置为 **🟩 绿色**。


### 第三步：设计 Prompt 模块 (Express)

1. 在绿色卡片右侧，创建一个新卡片。

2. 输入结构化提示词（使用 Markdown）：

    # Role

    会议纪要整理员

    # Task

    将左侧的会议记录整理为结构化的行动清单。

3. 设置为 **🟨 黄色**。

4. **建立连接**：从绿色卡片右侧拖拽连线至黄色卡片左侧。

### 第四步：模拟运行 (Simulate)

_（注：在未安装自动化插件前，我们使用“手动模拟”来验证逻辑）_

1. 复制“绿色卡片内容 + 黄色卡片内容”。

2. 发送给 ChatGPT/Claude。

3. 将生成结果复制回 Canvas，新建一个卡片放在右侧。

4. 设置为 **🟥 红色**。

### 第五部：引入评价与迭代 (Evaluate & Iterate)

1. 在红色结果卡下方，创建一个 **🟦 蓝色**卡片。

2. 写入 Critic 指令：“检查上述清单，是否有遗漏责任人？是否有截止时间？”。

3. 模拟运行 Critic，将修改意见填入蓝色卡片。

4. 创建一个新的 **🟨 黄色**卡片（Refine Prompt），连接“红色初稿”和“蓝色意见”。

5. 生成最终 **🟥 红色** 结果。

### 第六步：封装与编组 (Group)

1. 框选上述所有卡片。

2. 右键点击 -> **Create Group**。

3. 命名为“会议纪要生成模块 v1.0”。

4. _现在，你可以复制这个 Group，替换绿色的输入卡，复用整个流程。_

## 5. 进阶技巧：从模拟到半自动化

如果你希望在 Canvas 内直接运行 AI，推荐安装社区插件**Text Generator**或 **Canvas LLM**。

### **配置 Text Generator 在 Canvas 中运行：**

1. 确保已安装 `Text Generator` 插件并配置好 API Key。

2. 选中一个 **🟨 黄色 Prompt 卡片**。

3. 该卡片必须已经连接了 **🟩 前置上下文卡片**。

4. 呼出命令面板，搜索 `Text Generator: Generate Text`。

5. 插件会自动读取前置卡片作为 Context，读取当前卡片作为 Prompt，并将生成的文字**追加**在当前卡片内（或生成新卡片，视设置而定）。

## **6. 常见误区警示**

- ❌ **蜘蛛网连线**：连线过于杂乱，没有清晰的左右流向。

    - _修正_：利用 Group 整理区域，保持主干清晰。

- ❌ **颜色滥用**：随心情配色，导致协作者（或未来的你）看不懂逻辑。

    - _修正_：严格遵守绿黄红蓝四色规范。

- ❌ **Prompt 过于简单**：黄色卡片里只有一句“帮我总结”。

    - _修正_：黄色卡片应包含完整的结构化 Prompt（Role/Context/Task/Constraints）。
