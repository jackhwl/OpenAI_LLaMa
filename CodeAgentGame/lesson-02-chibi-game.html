课 Coding Agent 实战营 LESSON 02 · 1 天课程总纲

第二课 · 多模型协作的决策游戏（赤壁·风起）

11 月 18 日 · 1 天 ｜ 产出：一个可玩的决策游戏 + 一段对"规则与生成"边界的论述 先备知识：完成第一课；能用命令行启动一个 Python 脚本。

这一课在解决什么问题

让一个模型写一段文字，是很容易的事。 难的是：当你要做的不只是一段文字，而是一个有规则、有胜负、有代价的系统时， 哪些部分该交给模型，哪些部分绝对不能交给模型？

这一课用一个真实做出来的小游戏来回答这个问题。

题材：建安十三年，赤壁。 你扮演孙权帐中的决策者，经历 5 个关键节点，每个节点 3 个选择。 你的每一步都会改变四维态势，最终走向六种结局之一。

实验材料

先看懂架构：为什么需要一个"本地代理"

打开 index.html 你会发现：这个页面里没有任何 API Key。

浏览器 (index.html)                    本机 (server.py)                模力方舟
   │                                        │                             │
   │  POST /api/council/one {第几位, 局势}    │                             │
   ├───────────────────────────────────────>│                             │
   │                                        │  Bearer <Key>  —— 只有这里知道 │
   │                                        ├────────────────────────────>│
   │        {这一位的主张}                    │<────────────────────────────┤
   │<───────────────────────────────────────┤                             │

为什么是 /one 而不是一次问全五位？因为五个模型快慢差得远（实测 0.9 秒到几十秒）。 一次批量请求，页面得等最慢的那位，屏幕上只有一句"正在思量"——看上去跟卡死一样。 拆成五路之后，谁先想完谁先开口，等待是有形状的。 批量接口 /api/council 仍然保留，给脚本用（lab/tools/smoke_council.py）。

这是本课程第一个必须记住的工程习惯： 前端页面是会被用户打开的、会被分享的、会被 F12 看穿的； 任何密钥都不能出现在前端。 所有模型调用都要经过你自己写的后端。

启动后可以在终端看到代理的自我介绍：

步骤

第 1 步 · 下载项目、放进你的 Key、启动

这一课是跑在你本机的网页项目，不吃环境变量，只读自己目录下的 config.json。 所以除了第一课配好的 Agent，还要把这个仓库拉下来、把这枚令牌写进去。

① 把项目下载到本地

用 git（推荐，以后能 git pull 拿更新）：

git clone https://www.gitlink.org.cn/ccf-ai-infra/Coding-Agent-Bootcamp.git
cd Coding-Agent-Bootcamp

不用 git 也可以：打开仓库首页， 点右上角的「克隆/下载」→ 下载 ZIP → 解压，效果一样，只是以后更新要重新下。

② 把你的 Key 写进 config.json

最省事的做法：打开第一课配置中心的第 6 步， 它已经按你填的令牌生成好了命令，点一下复制、粘进终端回车就行。

手打版是这样（把 sk-... 换成你自己的令牌）：

cd lesson-02-chibi-game/lab
python -c "import json,shutil;shutil.copy('config.example.json','config.json');d=json.load(open('config.json',encoding='utf-8'));d['api_key']='sk-...';open('config.json','w',encoding='utf-8').write(json.dumps(d,ensure_ascii=False,indent=2));print('已写入 config.json')"

这条命令做三件事：复制模板 → 只替换 api_key → 其余模型配置（参谋团、生图、配音）原样保留。 比手动编辑安全，不会把 JSON 结构改坏。

Windows 请用 PowerShell（开始菜单搜 "PowerShell"），别用老的 cmd —— 命令里的引号在 cmd 下会被解析错。macOS / Linux 用系统自带的终端即可。

不想跑命令也行：把 config.example.json 复制一份改名 config.json，用编辑器把 <<在这里粘贴你的模力方舟访问令牌>> 换成令牌即可。

③ 启动

python server.py

第一次运行会看到一段自我介绍（见本节开头的示例），重点确认两行： API Key : 已载入、打开 : http://127.0.0.1:8848。

⚠️ 如果页面打不开，先怀疑本机代理。 很多开发机设了 http_proxy， 它会连 127.0.0.1 一起拦——现象是浏览器转圈或直接 ERR_...，而服务本身明明起来了。 解决办法是让回环地址绕过代理： - 起服务时：no_proxy="127.0.0.1,localhost" python server.py（出网仍走代理，这是对的） - 浏览器：加 --proxy-bypass-list="127.0.0.1,localhost" - 命令行验证：curl --noproxy '*' http://127.0.0.1:8848/api/status 一句话记住：出网要走代理，回环必须直连。 同一个进程里这俩都得满足。

看到 API Key : 已载入 就说明成功了，用浏览器打开 <http://127.0.0.1:8848>。

端口默认 8848，被占用时可以用 PORT=9000 python server.py 换一个。

第 2 步 · 完整玩一局

从头走到结局。游戏中注意观察四处：

  1. 每个节点都有 5 名谋士各自陈词 —— 点开看，他们不是同一个模型。

五位是同时开问的，谁先想完谁的卡片先出现，页头有"已陈词 x/5"和秒数。 某一位没配上 Key、超时或被平台限流，只会红一张卡，卡上有「重试这一位」。 实测五个里最快 0.8 秒开口、最慢那位 78 秒——所以页面必须边回来边显示。

  1. 每个节点右下角可以「查看提示词」 —— 真正发给模型的话，一字不改地摆在那里。
  2. 四维态势的变化（军心 / 水战 / 天时 / 曹疑）由选项的数值直接决定。
  3. 结局不是模型编的 —— 下面是这一课的核心。

第 3 步 · 读代码：结局是怎么决定的

打开 index.html，搜索 ENDINGS 和判定函数。

你会看到六种结局：东风有意（史实线）、火尽江寒（惨胜）、一纸降书（以诈取胜）、 南北分治（长期对峙）、铜雀春深、以及最罕见的投降线。

它们的判定完全由一段确定性代码完成，六条优先级规则，依次比对四维态势。 5 个节点 × 3 个选项 = 243 条路径，全部可以在本地暴力枚举跑一遍， 结果是六种结局都能到达（分布约 30% / 29% / 15% / 14% / 10% / 2%）。

模型在这套系统里的职责被严格限制为三件：

交给模型不交给模型
把"你选了 X、态势变成 Y"写成一段有画面感的战史叙述判定这一局赢还是输
把终局的态势写成一段收束断语决定态势怎么加减
画图、配音决定有哪些选项

为什么？ 因为模型的输出是概率性的。 如果让模型判胜负，那同一个操作在不同次运行里会有不同的结果—— 玩家就失去了"我在做决策"的感受，只剩下"我在抽奖"。

记住这句话：规则用代码，表达用模型。 这是这一课最值钱的结论。

第 4 步 · 亲手改一件事

现在轮到你了。挑一个改（改动越小越好，方便对比）：

改法 A（最简单）· 改数值 在 index.html 里找到任意一个选项的 d:{...}，把某个数字改大。 比如把「连船」节点里"火攻"的 naval 加成从 +3 改成 +1。 刷新页面重玩一局，体会结局如何变化。

改法 B · 改文案 在 prompts/base_rules.txt 里，你会看到四条"硬性约束"， 其中一条明确列出了模型可以提到的人物白名单（曹操、孙权、刘备、周瑜、鲁肃、黄盖……）。 试着往白名单里加一个人，或者删掉一条约束，重跑一次，看看叙述会不会"跑偏"。

ℹ️ server.py 里已经没有提示词副本了（2026-10-27 删掉）。以前它抄了一份 BASE_RULES 当兜底，结果是改 prompts/ 看不出效果、还以为"模型不听话"。 现在唯一来源就是 prompts/；万一文件丢了，server.py 会直接报错并告诉你 去仓库根目录跑 python tools/gen_prompts.py。改完保存即可，不必重启服务。

改法 C · 换模型 在 config.json 的 narrator_styles 里，把「快笔」的模型换成一个推理型的大模型。 你会明显感觉到变慢——慢到怀疑人生。原因见下面的"常见坑"。

第 5 步 · 记录你的对比

不管你改了哪一种，请记录：改之前是什么结局、改之后是什么结局、中间哪一步开始分岔的。

这份记录就是本课的交付物。

你会看到什么（验收标准）

  • 终端里打印出代理启动信息，API Key : 已载入
  • 浏览器打开后能进入第一幕，显示 5 名谋士各自的陈词
  • 每个节点底部的「查看完整提示词」能展开，system（人设与硬性约束）和 user 都能看到
  • 15 个选项都有插画（assets/choices/ 里的图被正确加载）
  • 完整走一局到结局，结局页有画面、有结束语、有与史实的对照说明
  • 你的第三、四步有一个可复现的改动，并且能说清它改变了什么

提示词档案：模型到底被下了什么命令

lab/prompts/ 下每个 .txt 都是真正发给模型的提示词，不是文档里转述的说明。 以 ## 开头的行是注释，不会发出去。

文件决定什么
base_rules.txt硬性约束：可用词汇、不许虚构什么
narrator_system.txt每一幕的文风
ending_system.txt结局断语的语气
council_system.txt5 名谋士的人格设定
consequence_user.txt / ending_user.txt / council_user.txt每一步的具体任务
image_style.txt插画的统一画风
stat_labels.json四个态势维度的名字（军心 / 水战 / 天时 / 曹疑）

面板上的每一段，分别来自哪个文件

游戏里点开「查看这一步发给 AI 的完整提示词」，会看到三段；结局页是两段。 每段标题下面都标着一个文件名，对应关系完整列在这里（除插画那行，其余都在 lab/prompts/ 下）：

面板上的段落改哪个文件改它会发生什么
[ system ] 人设与硬性约束narrator_system.txt、base_rules.txt前者管文风，后者管禁用词汇与人物白名单。面板里是两段拼接后的结果
[ user ] 这一步的具体任务consequence_user.txt字数上限、句数、能不能跳到下一场。{node}、{delta} 由服务端填，别删
[ 插画 ] 本选项的画面描述assets/choices/manifest.json 的 prompt 字段生成图片时就已写死；改 image_style.txt 只影响之后新生成的图
结局页的 [ system ] 与 [ user ]ending_system.txt、ending_user.txt断语的语气，以及结局判定看哪几个维度
参谋团的陈词council_system.txt、council_user.txt各人的身份与口吻、80 字上限。人数在 config.json 的 council

改法都一样：打开文件、改文字、保存。server.py 每次请求都重新读一遍这些文件， 所以不用重启服务，刷新页面重跑同一个节点就能把两次输出并排对比。 改坏了执行 git checkout -- lab/prompts/ 恢复。

换题材时，这几条必须改

最容易忘、也最致命的是 base_rules.txt 的第 3 条：

不得虚构史书中没有的人物姓名；可提及的人物仅限：曹操、孙权、刘备……

你要写的是家乡的那场战役，而这条不改，模型张口还是曹操孙权。 同理 council_system.txt 里的「汉末孙权帐中」、stat_labels.json 里的维度名 （你的题材里未必有"水战"），都要跟着你的题材走。

改完不用重启

server.py 每次请求都重读一遍这些文件。改完 .txt 刷新页面、再点一次同样的决策， 就能立刻看出差别——这是个很适合做实验的地方：把 narrator_system.txt 的语气 从「史书夹注」改成「说书人」，同一个决策会得到两种完全不同的叙事。

这些提示词能改吗

能。模型的行为几乎全部由这几个文件决定，改一张 .txt 就是一次干净的对照实验。

游戏里点开「查看这一步发给 AI 的完整提示词」，每一段旁边都标着它来自哪个文件—— 逐段对照见上面「面板上的每一段，分别来自哪个文件」那张表。 {占位符} 是服务端填进去的（比如 {delta}），别删。

几个现成的实验，都只改一行：

想验证什么改哪儿看什么
硬性约束到底起不起作用删掉 base_rules.txt 第 3 条的人物白名单模型会不会开始编人名
文风是不是提示词决定的narrator_system.txt 换成说书人口吻同一个决策的两种叙事
结局的语气由谁定ending_system.txt 删掉「史笔的克制」断语会不会变成抒情
参谋团为什么说话那么短council_system.txt 把「80 字以内」改成「300 字」五个谋士的陈词长度

每条实验的记录方式都一样：改之前先 cp 一份原文件，同一个节点跑两次，两段输出并排贴进打卡。 这就是「创新点」里最省力、也最容易复核的一条证据。

一条限制：插画那段改不动。它在你生成图片的时候就被写进 assets/choices/manifest.json 了，改 image_style.txt 只影响之后新生成的图， 已经生成的图不会变。要验证就把那张图重新生成一次，lab/tools/gen_choice_images.py 里 写死了 15 条画面描述和画风后缀。

弄坏了怎么恢复

git checkout -- lab/prompts/

把提示词摆出来不是为了好看。这一课要在打卡里回答「为什么结局判定不该交给模型」—— 答案的一半就写在 base_rules.txt 和 ending_system.txt 里： 模型服从的是你给的约束，而不是历史本身。

常见坑

未配置 API Key，请检查 config.json config.json 没建，或者建在了错误的目录。必须是 lab/config.json，和 server.py 同一层。

谋士们的回复很慢，甚至等很久只等到一两句 三个原因，按可能性排序：

  1. 你在用推理型模型（如 GLM-5.3）当参谋。这类模型的思维链不返回给你，

但会实打实花掉时间——2026-11-12 复测单次要 9~15 秒，历史记录里最慢到过 500 秒以上， 波动很大，别的模型都在 1 秒上下。

  1. max_tokens 给得太小。推理型模型会把额度全烧在思维链上，

然后返回一个空字符串且不报错。

  1. 平台限流。密集调用会返回 429，等一会儿再试。

这正是本课让你亲手换模型的用意：速度和质量是硬冲突的， 你得为自己的场景做取舍，而不是抄一个"最强模型"的名字。

生图报 参数无效 'size' 该平台的生图接口只接受白名单里的画幅。横屏基本只有一种可用。 config.json 里的 image_size 已经填的是可用值，别乱改。

页面里没有图，全是色块 说明 assets/choices/ 没被读到。检查你是不是漏拷了这个目录， 或者 manifest.json 里的路径和服务器的静态目录对不上。

终端里刷出一长串 traceback（ConnectionAbortedError / WinError 10053） 在 HTTP/1.1 长连接下，浏览器提前断开（刷新页面、关标签、关闭自动化脚本）时， 服务端写响应必然失败。这不是错误，_send 里已经吞掉了这类异常。 如果你看到它，说明你的代码是从更早的版本复制来的——补上那三行 except 即可。

端口被占用 PORT=9000 python server.py，然后用 9000 访问。

思考题

  1. 如果把结局判定也交给模型，会产生哪些具体问题？

请至少说出两个玩家能感知到的问题，而不只是"不够准确"。

  1. prompts/base_rules.txt 里为什么要专门写一条"不得虚构史书中没有的人物姓名"？

试着把这一条删掉跑一次，看看会发生什么，再把答案补完整。 这条规则与第三课的"三分法标注"是同一个问题的两种解法，想想它们的区别。

  1. 前端页面用 fetch 调用你自己的代理，和直接调用模型服务商的接口，

除了"藏住密钥"之外，还多出哪些能力？（提示：缓存、降级、限流、日志）

交上去以后怎么判

评审不看文笔，只看四件事：题材说清了没有、决策路径对得上没有、改动能不能落到具体文件、改前改后是不是各有一个结局。

请先换掉题材

我们不希望收到第二份赤壁。 示例只是示范这套东西怎么搭，请换成你自己的题材—— 你家乡的那场战役、地方志里某位人物的一次抉择、县志里记过的一件小事。 越本地越好，那是我们抄不到的。

换题材可以分几层做，做到哪一层都能交，只要在 Issue 里写清楚你停在哪一层、为什么停：

  • 只动了数值或文案（第 4 步那种改法）→ 交上来就是一份"改动对比"，这也算。
  • 换了剧本、还没换提示词 → 可以交。模型会用三国语气讲你的题材，这本身就是很好的观察材料。
  • 整条链路都换掉 → 见下面的清单。

要改的地方：index.html 里的 SCENES（5 个决策场景）与 ENDINGS（6 个结局）。 四项数值 morale / naval / fortune / cao 也可以换成你题材里的维度 （例如「粮草 / 人心 / 天时 / 敌势」）。

2026-10-27 我们派了三个学员从零试做，实测换题材要动 9 处。 下表是那次试做画出来的地图，不是门槛：照着改不会漏；只改一半，也知道自己漏了哪里。

自查的办法：随便点进一幕，看选项文字、配图、谋士头衔、态势名、封面标题 五处还剩几处赤壁的痕迹。五处全干净是一次完整换题材；还剩几处，就把那几处如实写进你的记录里 —— 那些"没换干净"的地方，往往比换干净了更有话说。

内容清单

  • 你玩的这一局的完整决策路径（5 个节点的选择）和最终结局
  • 你的改动：改了什么、为什么这么改
  • 改动前后的结局对比，以及你认为的分岔点
  • 一段 200 字以上的论述：为什么结局判定不该交给模型
  • 可选加分：往 config.json 的参谋团里加一个模型，观察它的陈词风格与别人的差异

创新点（请在 Issue 评论里单独写一段）

这一课的评分不看画面好不好看，看你动过哪一层、以及能不能说清楚为什么。 下面八个方向，挑一个写透（200 字以上，必须带对比证据），不必全写。 换题材的同学请顺手写清楚你停在哪一层（只改数值 / 换了剧本 / 整条链路换掉）和为什么停。

方向具体可以做什么拿什么当证据
换了题材家乡的那场战役、地方志里某人的一次抉择、县志里的一件小事；越本地越好五处赤壁痕迹的自查结果：选项文字、配图、谋士头衔、态势名、封面标题，还剩几处
改了判定维度四维 morale / naval / fortune / cao 换成你题材的维度（如粮草 / 人心 / 天时 / 敌势）改前改后的维度表；特别说明方向有没有反转（原「曹疑」越低越好，你的「敌骄」可能是越高越好）
改了结局规则增删结局、改六条优先级规则、加第七个结局枚举 243 条路径的输出：六种结局各自占比多少，有没有结局变成不可达

重新划了模型边界让模型多干一点或更少一点：例如只写比喻不写判断，或让模型参与评分但外面套一层确定性校验改前改后同一节点的两段叙述 + 说清哪部分仍然是代码说了算
改了提示词改 prompts/base_rules.txt 的人物白名单、增删一条约束，看叙述会不会跑偏同一节点改前改后的两段输出并排对比
改了玩法加玩家知情度、随机事件、回合时限、代价系统、多结局之外的结算口径新机制的截图 + 一局实测记录
改了性能与降级结果缓存、并发退避、生图降级链、失败重试一局总耗时前后对比（例如 78.5s → 多少）

这些不算创新点：改封面颜色、换题诗、把 SCENES 的文案替换成自己的题材但提示词没动且不作说明、 删掉结局里的 real 字段（那等于把这课最值钱的部分扔了）、只写"我的题材更有意思"。

自评模板（照这个格式写，三句话）：

我把 ______ 换成了 ______，因为 ______。 证据：______（改动前后对比 / 枚举输出 / 耗时数据）。 代价：这么做的缺点是 ______，下次我会 ______。

下一课

这一课里，所有的"事实"都是我们自己写死在代码里的—— 5 个场景是固定文案，结局是固定算法。模型只负责说得好听。

第三课要反过来：把真实的历史时间线摆在桌面上， 让用户自由输入改写其中一个节点， 然后让模型推演后续会发生什么—— 并且，给它套上三道枷锁，逼它对自己生成的每一条内容负责。
